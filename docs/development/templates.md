# Template implementation

The pure parser/renderer is `crates/core/src/template.rs`; the thin `crates/template-wasm` crate exports its owned-buffer ABI. Keep the core an rlib: mixing a core cdylib with separate desktop/workspace feature graphs can overwrite un-hashed build outputs in a shared Cargo target directory.

Content remains envelope version 1 with `type: template`, source text and variable definitions. Unknown non-reserved identifiers are text fields. Date/time/timestamp key:enter and cursor:here are reserved. Rendering is one pass: answers and defaults are never parsed as source. The template renderer receives one timestamp and local UTC offset, so evaluation has no IO.

Sync protocol 6 prevents old desktops exchanging rich-text records or assets they cannot retain. Public API routes stay v3. Code and legacy plain_text remain literal; Text uses the template renderer. Browser runtime answers only go to the local WASM module; native answers only go to the local Rust runtime and private IPC. No runtime answers are persisted or synchronized.

Omarchy snapshots retain stable identity/revision and a precomputed prompt flag. Immediate templates render on a worker while following typing is buffered through the existing insertion path. Prompted matches send a PID-validated notification before any erasure. The panel requests preparation using the original event deadline and input generation; only then does it open the fill form. Completion sends a fresh request after confirmation.

Private notifications remain datagrams; insertion uses a bounded Unix stream so long values cannot exceed a datagram limit. The service revalidates identity/access before each ordered text/Enter step. Acknowledgments carry input/context generation, preventing later steps after interruption. No completed Enter action is retried. Clipboard ownership/restoration uses the existing paste implementation.

Tests: core parser/clock/literal handling, SQLite metadata/snapshot identity, TUI dialogs, server import/move/conflict/Trash preservation, two offline clients, protocol rejection, real browser WASM/editor/fill/copy, and native panel controls. `scripts/template-smoke.py --live` requires explicit idle authorization, uses temporary data and disposable windows, and restores the original service/panel/focus.

`Rendered.cursor` is optional metadata: the marker’s UTF-16 offset plus suffix UTF-16 and grapheme counts. The source remains unchanged for sync/export; output text/steps omit the marker. Validation rejects duplicates, explicit Enter actions, Rich text and positions inside a rendered grapheme, including clusters formed by filled values. Older parsers reject the colon syntax. Clipboard payloads carry cursor metadata; confirmation Enter is consumed for marked snippets, and native movement occurs before buffered typing is released. No-marker serialization omits the field; deserialization defaults it to absent.

Browser input/textarea and Android selection use UTF-16 offsets. Chrome contenteditable and native desktop fallback paths move backward by graphemes using the editor’s character navigation. iOS uses a UTF-16 offset through UITextDocumentProxy, consistent with UIKit text-position offsets; host behavior still requires device acceptance testing. These host APIs can differ for bidi text, editor-specific arrow handling and pasted newline normalization. Cursor movement checks the existing target/generation/interruption state; failure never retries insertion. Copy ignores cursor metadata and reports the omission without changing text usage counts.

macOS and Windows capture the focused text control before paste and prefer direct placement through OS accessibility APIs: macOS `AXSelectedTextRange`, Windows UI Automation text ranges. Linux/Omarchy uses AT-SPI `SetCaretOffset`. These are platform adapters, without per-application cursor plugins. Direct placement requires matching pasted text, a collapsed selection, the original focused control, and verified cursor metadata. macOS uses UTF-16 ranges; Windows finds text ranges rather than assuming a character unit size. Unsupported controls retain arrow fallback; known text/selection/focus changes cancel positioning. After any attempted accessibility write, failure or uncertain readback cancels without adding arrows or retrying insertion. A provider can apply a timed-out write late, so cancellation cannot undo that provider behavior. Windows marked snippets use this verified path rather than the older Notepad-specific replacement. Windows and Linux still need native acceptance testing for this change.

Generic native and Omarchy fallback movement has no suffix-length cap or fixed total movement deadline. Linux tracks remaining movement in constant space, keeps the idle clock alive on progress, and waits for movement completion or service disconnection instead of a fixed IPC timeout. The existing worker stall watchdog remains active. Native input epochs cancel marked insertion/movement regardless of the trigger key, while TypeRelay injected events and captured macOS following typing are excluded. Omarchy prefers a verified accessibility caret jump; unsupported fields receive bursts of up to 16 cursor strokes, checking focus and pointer context before every stroke, then yielding and polling buffered input between bursts. Each stroke is one press/release/SYN packet; acknowledgment follows the final burst. This removes the per-character delay without queuing an unbounded sequence of input events.

Chromium/Electron applications must expose their editable content through accessibility for direct positioning. A window-only accessibility tree is insufficient. For the T3 Code Linux launcher, add `--force-renderer-accessibility` to `~/.config/t3code-flags.conf` and fully restart T3 Code. With Rich text composer disabled, the shipped T3 editor and a 2,808-character suffix were verified using native clipboard insertion: exact placeholder placement, zero Left-arrow events, and the placeholder visible before typing. This was an isolated editor test; a running T3 process does not pick up launcher flags until restarted. Other application launchers may use different flag files.

Rich editors can transform pasted Markdown into lists, marks, or embedded nodes. Source grapheme counts then need not match cursor navigation. Direct placement deliberately requires matching text; rich-mode correctness is not established by a plain-text test. A successful caret change also does not guarantee viewport scrolling in every application (VS Code remains unverified). Changing clipboard insertion mode does not address either limitation: Linux already pastes text before positioning the cursor.

Run `python scripts/template-smoke.py --live --cursor-only --binary-dir <build-directory>` on an idle authorized Linux desktop. The default uses ordinary Chromium accessibility settings; repeat with `--cursor-accessibility disabled` to exercise fallback and `--cursor-accessibility forced` to require direct placement. The smoke test checks exact text and typing at the marker, long Unicode/multiline suffixes, elapsed insertion time, and focus cancellation after movement begins. A global key already in flight can cross a focus change (also observed in the original single-key loop); the regression allows at most that one key and rejects continued movement or an entire burst reaching the new window.

macOS regression coverage uses `scripts/macos-cursor-fixture.swift` and `scripts/macos-cursor-smoke.swift`. Run only on an idle authorized desktop, with the tested signed TypeRelay build using a disposable profile and `trigger_prefix: ';'`. Before its first launch, save `swift scripts/macos-cursor-smoke.swift --fixtures` into `<profile>/typerelay/snippets/cursor.yml`. Start TypeRelay with `XDG_CONFIG_HOME=<profile>`, then run `swift scripts/macos-cursor-fixture.swift <test-directory>` and `swift scripts/macos-cursor-smoke.swift <test-directory>` in the logged-in GUI session. The test directory must already exist; `/usr/bin/swift` needs Accessibility permission. A system/SSH audit session is not equivalent to the GUI session. Stop the fixture and disposable TypeRelay instance after testing.

The macOS fixture records exact text/caret positions and counts accessibility writes and Left-arrow events. Cases cover long text, Unicode grapheme boundaries, start/end markers, repeated text, Enter confirmation, following typing, unsupported setters, rejected/delayed writes, same-window focus changes, and text/selection changes during paste. Results are written to `fixture-results.json`. Also test a normal editor such as TextEdit: a synthetic NSTextView fixture cannot establish compatibility with every editor.
